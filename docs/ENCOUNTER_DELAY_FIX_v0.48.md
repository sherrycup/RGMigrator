# 0.48 战斗与开门延迟追加修复

2026-10-15，针对直接执行版中拾取已改善、战斗和开门仍慢的反馈。正式输出另建 `../output/0.48/fix-encounter-delay/黎之闪翼（开发中）_Godot`，从原RM通过Validator→MigrationPipeline重新迁移，保留历史输出。

## 已定位的来源

- 普通拾取不触发自动撤回记录，怪物与满足钥匙条件的黄、蓝、红门会触发。记录完成前地图和输入暂停。此前七事件探针未包含开门，也没有单独记录触发到检查完成的延迟；本次新增原Map010 EV056/057/058三种门与EV070战斗，保留EV022作参照。
- 私有诊断中，开启记录时触发前准备约0.4–0.54秒，仅在测试中关闭记录后相应等待降至约4–6ms。正式工程保留撤回功能。
- 分帧检查每处理一个容器/字段就调用场景归属检查，诊断样本每事件约6500次；为减少卡帧而使用的3ms预算把这些重复工作分散到很多帧，形成可感知的输入延迟。检查公共事件是否存在还会深复制整份事件命令和绑定。完整存档图也被重复遍历。
- 战斗后公共事件14首次请求升级动画21时，还存在纹理加载和动画编译峰值；原公共事件5含等待5，按既有原生命令秒数约定是250ms。开门还有强制转向路线及等待结束。这些正常事件时间不能全部计为卡帧，也不能擅自删除。

## 实现和保持的边界

1. 分帧预算回调在实际让出/恢复帧及最终发布时验证完整场景/代次/请求归属，在同步小步骤间只检查取消代次。主线程不让出期间现场归属不会被其他线程改写。重置、换图及取消仍不得发布过期记录。
2. 图验证批量处理至多32个容器后检查预算，保留原节点/深度/元素/数值限制、循环共享关系和对象类绑定检查。自动记录使用6ms软预算，捕获耗时也计入首次预算，避免捕获后在同一帧继续积累整段检查。这不是单帧硬上限。
3. 存档数据图与对象类绑定合为同一次遍历；类/方法结构、继承、来源哈希以及角色、事件和表现现场的完整恢复校验继续执行。旧存档缺少脚本数据时保留对应兼容检查，不省略数据验证。同步与分帧实现仍由 `tools/sync_save_preparation.py` 保持一致。
4. 只读定义在准备阶段复用，存在现场覆盖时仅合并对应记录；查询公共事件引用不再深复制指令树。修复默认参数被提前求值而无条件复制自定义数据和转换常量的问题。
5. 进入地图时，依据源脚本的静态动画赋值、角色初始动画和原动画常量准备原始动画。只预取只读资源，不执行AST；现场/测试覆盖仍重新解析验证，未使用的错误引用仍在实际使用时报告。播放进度和材质仍归各实例，代价是进入地图时多做少量预加载。

源公式、公共事件5的等待和门动画路线均保留。脚本直接修改正式状态及报错弹窗后退出的行为沿用上一版。所有游戏节点捕获和存档校验仍在主线程，后台仅写已经脱离现场的数据。

最终正式输出、回归及前后测量见 `tests/VERIFICATION_v0.48_ENCOUNTERS.json`。测试关闭VSync、使用Dummy音频且窗口位于屏幕外；不修改正式工程显示/音量设置。不能据少量事件宣称全部地图稳定60FPS。
