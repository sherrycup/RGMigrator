# 0.5 事件等待与显伤线程

2026-10-16按用户要求将本次修复更名0.5，并在验证后提交、推送GitHub。交付目录为`../output/0.5/final/黎之闪翼（开发中）_Godot`，从原RM重新运行正式迁移流程；历史工程保留。

战斗/开门的等待有两部分：事件前撤回记录准备，以及原公共事件/移动路线的等待、动画。0.49的`refresh_damage`还会在事件中逐个计算全地图敌人，显伤预估的缓存进入状态图后又增加下一次快照成本。不能把完整事件时长全部视作卡帧。

`FlashEnemyMapLabels`现在只在主线程构造复制的角色、敌人、技能、常量输入。`FlashDamageWorker`使用单个常驻线程和Semaphore/Mutex邮箱，更新时唤醒，待处理任务仅保留最新一份。只读脚本也可能发出状态通知，因此相同输入不会重新排队或使正在计算的结果过期。线程只执行纯战斗模拟，缓存仅存在线程内，不访问节点、纹理、RuntimeState、全局技能注册表或正式战斗缓存。绘制和节点归属检查留在主线程。

后台结果只有请求版本、地图编号和地图代次均匹配时才能发布。队伍属性、技能目录、敌人HP/耐心/状态、换图和撤回都会产生新输入。关闭场景时唤醒并回收线程。线程计算错误交回主线程，沿用错误弹窗并退出1的策略。

怪物在`begin_battle!`中已经可能HP归零，而`finish_battle!`及公共事件23的删除随后才完成。以前此间重新求值会把死亡敌人显示成0。现在提交结果、每帧清理及真正绘制时均检查敌人HP/死亡标志/事件删除状态；致死后立即隐藏标签。非致死的pending结果仍保持原战斗预测，实际血量、奖励和消失时序由原事件负责。

`FlashMapBridge.refresh_damage`改成请求显示刷新。`got_damage`等脚本getter、怪物图鉴和实际开战仍按需同步计算，保持原公式。地图显伤不再向可保存状态写入整图预估缓存。

撤回仍保存事件执行前的完整现场，并在完整验证后才启动事件。捕获时的`SaveGraph.clone_checked`合并脱离与资源/预算检查；快照脱离后，对象图及类链接的同一有界检查交给线程。Schema、资源引用和恢复实例检查继续在主线程分帧完成；整图已验证的嵌套分组复用检查结果，仍执行各自结构和引用验证。独立读档、Custom.restore及普通SaveCodec.prepare不会跳过其校验。取消、重置、换图、退出会回收工作并拒绝过期编号。`SavePreparation.gd`继续由`SaveCodec.prepare`生成，使用`tools/sync_save_preparation.py --check`核对。

验证数据见`tests/VERIFICATION_v0.5.md`及同名JSON。测量包含原Map010三种钥匙门、拾取、战斗，分别记录输入同步耗时、撤回准备、完整事件及最大帧间隔。显伤输入准备、真实战斗的单敌人模拟、显式存读档/撤回仍有主线程工作；不承诺所有地图稳定60帧。原图形UI还原及原生GDScript事件编辑仍待完成，不能以版本号代替这两项验收。
