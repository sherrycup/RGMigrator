# 0.4 脚本迁移计划

2026-10-11规划稿。当前交付版本仍为ver0.39，编辑器由用户验收；本次只整理任务，不启动0.4实现。以下小版本按依赖顺序安排，0.40盘点后可根据实际脚本调整单项工作量。

## 大版本目标

把现有两个RM工程中实际使用的Ruby脚本逻辑迁入Godot，并补齐此前因脚本未接入而暂缓的事件、数据、魔塔玩法和自定义界面。交付以实际游戏流程和数据结果为准，不能把“源码已导出”“语法可解析”或“生成工程能启动”当作脚本功能完成。

继续遵循Windows、Godot标准版、Compatibility、纯GDScript的工程约束。RM原生回合制战斗、原生战斗事件及原生Troops功能仍不纳入；项目将同名类改作楼层怪物等用途时，按实际功能迁移。RTP迁移、读取RM旧存档不在本轮范围，新Godot存档需要覆盖迁移后的自定义状态。

## AST与迁移路线

需要构建AST，但这里属于源码转译。`RmxpDataConverter._export_scripts()`已经能够从`Scripts.rxdata`解压并解码Ruby源码；后续不是从机器码恢复源码，而是理解源码并生成Godot实现。

```text
源码提取与加载顺序
    → Ruby词法/语法分析 → AST（保留脚本ID、名称、行列）
    → 语义分析（作用域、类重开、方法覆盖、alias、调用依赖）
    → 中间表示IR（统一表达状态访问、方法调用、等待与显示操作）
    → GDScript生成 + Ruby语义/RGSS服务适配
    → 静态检查、真实运行与流程验收
```

AST表示代码结构，不能独自解决Ruby与GDScript的语义差异，也不能替代RGSS的绘图、窗口和游戏状态。建议采用“通用语法转换＋现有Godot服务适配＋特殊插件等价实现”的路线。先打通小段真实脚本的全过程，再扩展覆盖面。

解析器在0.40确定：优先评估用户提供的RM-sync静态AST/语义分析实现，参考其结构和规则，将适合的部分移植为纯GDScript，并用真实工程建立语法样本；补齐转译需要的语法节点和诊断。成熟解析器可以用于设计参考或经明确架构决策后接入；不能默认引入Ruby环境、C扩展或要求玩家安装外部运行时。现代Ruby解析器能生成AST，也不等于已经验证了RMXP旧Ruby语法及语义的兼容性。

源码评估表明，当前`RubyAstDocument`主要保存作用域树和符号索引，`ParseDocument`扫描源码收集声明及推断类型；适用于编辑器的静态分析。用于转译时需要补齐以下部分：

- 表达式和语句的完整节点及子节点关系，包括运算优先级、调用参数、赋值目标、条件各分支、块内容和返回/异常路径；不能只保留名称和推断类型。
- 严格词法/语法诊断和明确的未支持节点。当前扫描器会在文末收拢未闭合作用域，转译器应区分编辑中的不完整源码与可生成代码的完整输入；字符串插值、正则和heredoc等需用真实样本验证。
- 对Ruby标识符按大小写区分；参考实现多处使用`OrdinalIgnoreCase`服务符号查询，移植为编译语义时必须调整。
- 保留同名方法的定义顺序和版本。参考索引合并会按同名方法替换记录，转译还需保留`alias`捕获旧实现、类重开和后续覆盖形成的调用关系。
- 保留源位置并确定字符位置换算；C#字符串索引与GDScript字符/文件字节位置不能直接混用。
- 补齐IR、GDScript生成与现有游戏服务接入。这些不由编辑器的作用域及符号分析直接提供。

本轮结论来自源码阅读，尚未用两个RM工程运行其分析器验证覆盖率。0.40应先建立真实语法样本和差异清单，再确定移植边界；以参考和扩展已有设计为起点，不直接引入.NET或原编辑器的界面依赖。

## 已核对的现状与难点

- 当前迁移器保留Ruby源码，生成工程尚无Ruby解析器、转译器或执行接入。编辑器通过`EditorScriptAdapter`将脚本相关指令变成保留原数据的注释占位。
- 两个工程均存在动态`eval`；二律背反的事件脚本实现还合并连续355/655，并通过脚本结果决定是否继续执行。迁移时要核对实际Interpreter覆盖，不能只套标准命令行为。
- 样板有同名类追加定义、`alias`和对Array/Hash等基础类的改写。方法别名必须保留定义当时的实现，不能简单把最后一个同名方法覆盖所有引用。
- 样板的`Game_Party.gain_currency`使用动态调用管理多种货币；`Game_Object.load_data`从自定义文本解析属性并使用`eval`；`Game_Troop`实际保存楼层怪物排列。这些属于需要补齐的项目功能。
- 两个工程都有Win32API相关脚本；样板还包含Bitmap插件的原生DLL调用。需要区分实际依赖、可用Godot替代的效果及未使用代码，不能直接转换DLL函数名并宣称可用。
- 当前运行时通过`RuntimeState`、`EventScheduler`、`EventUIBroker`及多个显示/数据服务组合工作。适配层必须接入这些入口，避免再建立一套不同步的开关、角色、背包或存档。

## 实施和完成判定

1. 每个脚本/功能区分“自动转译”“适配实现”“需人工处理”“不在范围”，再分别记录解析、生成、运行、行为验证状态。覆盖率按语法、调用接口和实际功能统计，不能仅按文件数或源码行数计算。
2. 不支持的语法或调用不得生成空函数、默认真条件或假成功。输出脚本名称、行列、依赖链；事件错误同时给出地图/事件/页或公共事件、指令位置。依赖未迁移方法的功能不能标为可运行。
3. 编译输入优先来自原始脚本和指令；对已编辑工程，利用`_editor_original`/原路线等保留信息设计恢复与冲突校验。不能丢失已编辑指令，也不能仅因支持355就无条件恢复所有脚本条件和路线。
4. 标准功能复用现有Godot服务，自定义覆盖通过明确入口接入。全局对象包装读写同一份`RuntimeState`，保持事件刷新、界面通知和存档一致性。只读数据库定义和可变实例状态分开。
5. 可确定内容的eval可解析转译，有限的动态方法选择可转为显式分派；无法静态确定的代码生成、反射或原生内存访问，必须有范围明确的适配实现或列出人工任务。AST本身不承诺通用处理任意动态Ruby。
6. 尽量在迁移/重新转换时生成代码，运行时加载可复用结果；不每帧重新解析整个源码。性能主要检查动态分派、绘图、窗口刷新、等待调度、存档大小及内存，使用实际工程数据评估。
7. 测试除解析结构外，还需验证语义差异、方法覆盖/alias、块返回、状态同步、等待恢复、异常、交易与保存。整合阶段在同一流程中组合脚本条件、地图移动、玩法结算、UI和读档。
8. 源RM工程只读，不执行源Ruby；保持已有0.39验收输出。进入实现后每个交付版本按仓库规则重新正式迁移两工程到新的版本目录，不覆盖历史工程。
